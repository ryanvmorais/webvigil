# 003 — Web UI — Design

Traceability: every component and decision below cites the requirement(s) it satisfies
(`— RF-NN` / `— RNF-NN`). Requirements are in [requirements.md](requirements.md).

## Overview

`web/` is a Next.js (App Router) application, TypeScript strict, that is a **thin browser
client of the spec-002 Web API**. It renders what the API returns and holds no scan or
finding state of its own beyond the TanStack Query cache (RNF-01). It never talks to the
engine and adds no scanning capability.

```
browser
  │  same-origin  /api/*  and  /login /setup /scans …
  ▼
web/  (Next.js — `next dev` / `next start` / standalone `server.js`)
  │  next.config rewrite:  /api/:path*  ──►  ${API_PROXY_TARGET}/api/:path*   (server-side proxy)
  ▼
webvigil.api  (FastAPI, spec 002 — owns the HttpOnly session cookie)
  ▼
webvigil.core.Orchestrator  (unchanged)
```

The Next server proxies every `/api/*` request server-side (dev **and** prod), so the
browser only ever sees one origin, the `SameSite=Lax` cookie works with no CORS, and no
API base URL is compiled into the bundle (RF-01, RNF-06, ADR-3).

A page is: **client component → TanStack Query hook → typed `api.ts` wrapper → `fetch("/api/…",
{credentials:"include"})` → render**. Auth is a client-side guard: the app asks
`GET /api/setup` and `GET /api/auth/me` and redirects to `/setup` or `/login` as needed
(ADR-2). Live data (scan list, scan detail) is kept fresh by polling, gated on
non-terminal status and tab visibility (ADR-5); there is no SSE/WebSocket.

## Components

### Typed API layer — RF-03, RNF-07

**`scripts/dump-openapi.py`** imports `webvigil.api.app.create_app(WebConfig(database_path=":memory:"))`,
calls `app.openapi()`, and writes pretty-printed JSON to `web/openapi.json` (no DB, no
lifespan, no network). Committed.

**`pnpm gen:api`** runs `openapi-typescript openapi.json -o src/lib/api-types.ts`. The
committed `api-types.ts` is drift-checked in CI: regenerate both files, `git diff
--exit-code`, fail with "run `pnpm gen:api`" (RF-03, RNF-08).

**`src/lib/api.ts`** — one wrapper over `fetch`:

```ts
export type ValidationItem = { loc: (string | number)[]; msg: string; type: string };
export class ApiError extends Error {
  constructor(readonly status: number, readonly detail: string | ValidationItem[]) {
    super(typeof detail === "string" ? detail : "validation error");
  }
}

async function request<T>(path: string, init?: RequestInit): Promise<T> {
  const res = await fetch(path, { ...init, credentials: "include",
    headers: { "content-type": "application/json", ...init?.headers } });
  if (res.status === 204) return undefined as T;
  const body = res.status === 204 ? null : await res.json().catch(() => null);
  if (!res.ok) throw new ApiError(res.status, body?.detail ?? res.statusText);
  return body as T;
}

async function requestBlob(path: string): Promise<Blob> { /* credentials: "include"; throws ApiError */ }

export function fieldErrors(err: unknown): Record<string, string> { /* 422 loc[-1] → msg */ }
```

- Every response/request type is derived from `api-types.ts` `paths` (e.g.
  `type ScanOut = paths["/api/scans/{scan_id}"]["get"]["responses"][200]["content"]["application/json"]`).
  The wrapper exports a small `api` object (`api.login(body)`, `api.listScans(params)`,
  `api.report(id, fmt, download)` → URL string, `api.reportBlob(id)` …) so components never
  build paths by hand.
- `credentials: "include"` on every call (RF-03). Cookie is `HttpOnly`; JS never reads it
  (RNF-06).
- `report(id, fmt, download)` returns the **string** `/api/scans/{id}/report?format={fmt}&download={download}`
  for `<a download>` (RF-27). `reportBlob(id)` fetches `?format=html&download=false` for the
  preview (RF-28).

### Server-state (TanStack Query) — RF-04

`src/lib/query-keys.ts` — one key factory, namespaced per resource:

| Key | Endpoint | Options |
|---|---|---|
| `keys.auth.me()` → `["auth","me"]` | `GET /api/auth/me` | `retry: false`, `staleTime: 30_000` — drives the guard |
| `keys.setup()` → `["setup"]` | `GET /api/setup` | `retry: false` |
| `keys.health()` → `["health"]` | `GET /api/health` | settings page only |
| `keys.checks()` → `["checks"]` | `GET /api/checks` | `staleTime: 5min` — shared by RF-19 and RF-29 |
| `keys.defaults()` → `["config","defaults"]` | `GET /api/config/defaults` | `staleTime: 5min` |
| `keys.scans.list(filters)` → `["scans","list",{status}]` | `GET /api/scans` | `useInfiniteQuery`, `getNextPageParam: p => p.next_cursor`, polling (below) |
| `keys.scans.detail(id)` → `["scans","detail",id]` | `GET /api/scans/{id}` | polling (below) |
| `keys.scans.findings(id,f)` → `["scans","findings",id,{severity,checkId}]` | `GET /api/scans/{id}/findings` | `enabled` when the scan exists |

Mutations and the keys they invalidate:

| Mutation | Endpoint | On success |
|---|---|---|
| `useSetup` | `POST /api/setup` | `router.replace("/login?setup=done")` |
| `useLogin` | `POST /api/auth/login` | `invalidate(keys.auth.me())`; `router.replace(next ?? "/scans")` |
| `useLogout` | `POST /api/auth/logout` | `queryClient.clear()`; `router.replace("/login")` |
| `useChangePassword` | `POST /api/auth/password` | toast success; reset the form |
| `useCreateScan` | `POST /api/scans` | `invalidate(["scans","list"])`; `router.push("/scans/{id}")` |
| `useCancelScan` | `POST /api/scans/{id}/cancel` | `invalidate(keys.scans.detail(id))` + `["scans","list"]` |
| `useDeleteScan` | `DELETE /api/scans/{id}` | `invalidate(["scans","list"])`; `router.replace("/scans")` |

**Global 401 handling** (RF-04, RF-10): the `QueryClient` is built with a
`QueryCache({ onError })` and `MutationCache({ onError })` that, on `ApiError` with
`status === 401`, call a module-level `onUnauthorized()` callback. `providers.tsx`
registers that callback with access to `useRouter`: it clears the cache and navigates to
`/login`. If `queryClient.getQueryData(keys.auth.me())` was truthy when the 401 fired, the
redirect adds `?reason=expired` and the login page shows "your session expired" (RF-10)
instead of a bare login form.

### Auth guard and setup gate — RF-05, RF-08

`auth-guard.tsx` wraps the `(app)` route group:

```
1. const setup = useSetupStatus()          // GET /api/setup, retry:false
2. if setup.isLoading            → <FullPageSpinner/>
3. if setup.data.needs_setup     → redirect("/setup")
4. const me = useMe()                        // GET /api/auth/me, retry:false
5. if me.isLoading               → <FullPageSpinner/>
6. if me.isError (401)           → redirect(`/login?next=${encodeURIComponent(pathname)}`)
7. else                          → render children
```

The `(auth)/layout.tsx` is the mirror: if `needs_setup` and not on `/setup` → `/setup`; if
`me` succeeds → `/scans`. `/login` and `/setup` never call `useMe` themselves, so a
logged-out visitor there produces no 401 loop (Risks). After login the page reads
`useSearchParams().get("next")` and returns the user to the originally requested path
(RF-08).

Next middleware is **not** used for auth — the session cookie is `HttpOnly` and validated
only by the API, so the middleware could at best check for the cookie's presence, not its
validity (ADR-2).

### App shell — RF-02

`app-shell.tsx`: a `<header>` landmark with the product name (link to `/scans`), nav links
**Scans · Checks · Settings**, and a **Log out** button (calls `useLogout`). Below it a
`<main>` landmark holds the page. On a narrow viewport the nav collapses into a
`dropdown-menu` trigger; the page body never scrolls horizontally. Light/dark follows the
OS via Tailwind `darkMode: "media"` and CSS-variable tokens in `globals.css` — no toggle in
003 (ADR-8).

### Scan list — RF-11, RF-12, RF-13, RF-14

`scans/page.tsx` (the app home; `/` redirects here):

- `useScanList({ status })` — `useInfiniteQuery` over `GET /api/scans?limit=20&status=&cursor=`.
  The status filter comes from `useSearchParams()` and is written back to the URL by
  `status-filter.tsx` (`queued/running/completed/failed/cancelled/interrupted/all`); changing
  it resets to the first page (RF-12).
- `scan-list-table.tsx` renders: target, mode badge, scope, status badge, `severity-summary`
  (from `counts`), created time (`format.relativeTime` with the absolute value in `title`),
  and a row link to `/scans/{id}` (RF-11).
- "Load more" appears when the last page has `next_cursor`; it calls `fetchNextPage()` and
  appends (RF-11).
- **Polling** (RF-13): `refetchInterval` returns `3000` when `document.visibilityState ===
  "visible"` **and** any loaded row's status is `queued` or `running`, else `false`.
  `refetchIntervalInBackground` stays `false`, so a hidden tab never polls.
- Empty list → `error-states.tsx` `<Empty>` with a "New scan" CTA (RF-11).
- A "New scan" button routes to `/scans/new` (RF-14).

### New scan — RF-15..RF-19

`scan-form.tsx`, built on the shadcn `form` (react-hook-form + zod):

- On mount: `useScanDefaults()` pre-fills `mode=passive`, `scope=host`, `max_pages`,
  `delay_ms`, `follow_robots`; `fail_on` is rendered read-only with a note that the API has
  no exit code (RF-15).
- Fields: `target` (required), `mode` (passive/active `select`), `scope`
  (host/subdomains `select`), `max_pages` (int > 0), `delay_ms` (int ≥ 0), `follow_robots`
  (toggle), `disabled_checks` (multi-select from `useChecks()`, showing id · name · category
  · default severity — RF-19), `authorized_by` (text, shown only when `mode=active`).
- **zod schema mirrors the API** (RF-16): `target` non-empty and URL-ish;
  `mode==="active"` ⇒ `authorized_by.trim().length > 0` with the message "active scans
  require an authorization attestation" (spec-002 RF-08). The API's 422 is still
  authoritative and is mapped back onto fields via `fieldErrors()` if something slips
  through (RF-16, RF-18).
- **Active-Mode warning** (RF-17): when `mode=active`, a visible `role="alert"` block states
  that active scans send potentially intrusive traffic and must only target authorized
  systems, linking to `SECURITY.md`.
- Submit → `useCreateScan()` → `POST /api/scans` → on 201 `router.push("/scans/{id}")`,
  which shows `queued` then `running` (RF-18).

### Scan detail and findings — RF-20..RF-26

`scans/[id]/page.tsx`:

- `useScan(id)` → `GET /api/scans/{id}`. 404 → `<NotFound>` with a link back to the list
  (RF-20).
- Header shows target, status badge, mode, scope, `authorized_by` (if active),
  `tool_version`, `pages_scanned`, created/started/finished times, the applied `options`,
  and — for `failed` — the `error` string (RF-20).
- **Polling** (RF-21): `refetchInterval` returns `2000` while status is `queued`/`running`
  and the tab is visible; on the first terminal read it stops and
  `invalidate(keys.scans.findings(id))` runs once.
- `severity-summary.tsx` renders `counts` as chips (`2 high · 3 medium · 1 low`) — RF-24.
- `findings-table.tsx` → `useFindings(id, { severity, checkId })` → `GET
  /api/scans/{id}/findings?severity=&check_id=`. Rows render **in the order the API
  returns** (severity desc, check id, url, key — RNF-01; the UI never re-sorts): severity
  badge, title, check id, location (url + param/header/cookie), confidence badge (RF-22).
- A row expands (local React state, extra `<tr>`) to show description, remediation, each
  evidence blob as a labelled `<pre>`, CWE ids linked to
  `https://cwe.mitre.org/data/definitions/{n}.html`, and references as links (RF-22).
- Filters (min severity `select`, check id `select` from `useChecks`) are held in the URL
  query and drive the refetch (RF-23). Two distinct empty states: "no findings match this
  filter" vs "this scan produced no findings" (RF-23).
- **Cancel** (RF-25): shown only for `queued`/`running`; opens a confirm `dialog` →
  `useCancelScan()`. A 409 (lost race) → toast + refetch; the control then hides.
- **Delete** (RF-26): shown only for terminal scans; confirm `dialog` → `useDeleteScan()` →
  back to the list. For non-terminal scans the control is disabled with "cancel the scan
  first".

### Reports — RF-27, RF-28

- `report-menu.tsx` (`dropdown-menu`): enabled only when status ∈ `{completed,
  interrupted}` (a completed scan with zero findings still yields a valid empty report);
  otherwise disabled with a hint. Each item is an `<a href={api.report(id, fmt, true)}
  download>` — same-origin through the rewrite, so the `HttpOnly` cookie is sent and the API
  responds with `Content-Disposition: attachment; filename="webvigil-{id}.{ext}"` (RF-27).
- `report-preview.tsx`: a `dialog` containing `<iframe sandbox="" src={blobUrl}>` where
  `blobUrl = URL.createObjectURL(await api.reportBlob(id))` (HTML, `download=false`). Empty
  `sandbox` blocks scripts and same-origin access; the object URL is revoked on close
  (RF-28, ADR-7).

### Check catalogue — RF-29

`checks/page.tsx` → `useChecks()` → `GET /api/checks`. A `table`: id, name, category, mode,
default severity, CWE ids (linked), references (linked); filterable by category and mode,
sortable by severity. Cached (`staleTime: 5min`) and reused by the scan form's
`disabled_checks` control (RF-19).

### Settings — RF-30

`settings/page.tsx`: a change-password form (current + new ≥ 8, confirmed) →
`useChangePassword()` → `POST /api/auth/password`; on 204 a success notice and the form
clears; a 403 maps to an inline error on the current-password field. The page also shows
the API version from `useHealth()` (`GET /api/health`) and a **Log out** control (RF-30).

### Error presentation — RNF-07

One mechanism per error class, via `error-states.tsx` and the `sonner` toaster:

| Situation | Presentation |
|---|---|
| 422 / 403 on a form | field-level messages from `fieldErrors()` (or the single `detail` string) |
| a failed action (cancel/delete race, report fetch) | `sonner` toast, `aria-live` polite |
| 404 (scan not found) | full-page `<NotFound>` |
| failed initial load of a page's primary query | full-page `<LoadFailed>` with a Retry button |
| 401 anywhere | global handler → `/login` (RF-04) |

Raw stack traces and `[object Object]` never reach the user (RNF-07).

## Data model

The UI has **no persistent model**. Its only state is the TanStack Query cache (keyed as
above) plus ephemeral URL query params (`status`, `severity`, `check_id`, `next`,
`reason`, `setup`) and local component state (expanded rows, open dialogs, unsent form
input). All wire types are generated into `api-types.ts` from `openapi.json` (ADR-4); the
relevant shapes are `ScanSummary`, `ScanOut`, `FindingOut`, `CheckOut`, `ScanDefaults`,
`HealthOut`, `UserOut`, and `Page<ScanSummary>` (spec-002 `schemas.py`).

## ADRs

### ADR-1 — Plain `web/` subdirectory, no workspace tooling
**Decision:** `web/` is a standalone Next.js project with its own `package.json` and
`pnpm-lock.yaml`. No pnpm workspace, no Turborepo, no shared `node_modules`.
**Alternatives:** a pnpm/turbo monorepo spanning both stacks.
**Why:** decision 1 with Ryan. The Python and JS stacks share nothing but the OpenAPI
schema (a generated file), so workspace tooling would add configuration for no reuse.
**Trade-off:** two lockfiles and two install steps; CI runs `uv sync` and `pnpm install`
separately.

### ADR-2 — Client-side auth guard; no Next middleware, no BFF
**Decision:** the browser calls the API directly through the rewrite; the API owns the
`HttpOnly` cookie. A client component (`AuthGuard`) gates the `(app)` routes by querying
`GET /api/setup` and `GET /api/auth/me`.
**Alternatives:** Next middleware inspecting the cookie; a Next BFF holding its own session
and doing SSR of authenticated data.
**Why:** the cookie is `HttpOnly` and only the API can validate it — middleware could check
presence, not validity, and would duplicate auth logic. A BFF means a second session store
and server-side data fetching, explicitly a non-goal (requirements §Non-goals).
**Trade-off:** a brief full-page spinner on first load while `setup` + `me` resolve;
protected pages are client components (no RSC data fetching for authed data).

### ADR-3 — The Next rewrite proxies `/api/*` in dev and prod; no CORS
**Decision:** `next.config` rewrites `/api/:path*` to `${API_PROXY_TARGET}/api/:path*` in
every environment. The browser only ever makes same-origin requests; `web.cors_origins`
stays empty.
**Alternatives:** direct cross-origin calls from `next dev` (:3000) to the API (:8000) with
`web.cors_origins` configured for the dev server (as sketched in the requirements Context).
**Why:** one code path for dev and prod, no `Access-Control-*` handling, `SameSite=Lax`
just works, and no API base URL in the bundle (RF-01, RNF-06). Next rewrites are applied
server-side by `next dev`, `next start`, and the standalone `server.js` alike.
**Trade-off:** the dev API is reached through the Next dev server, not hit directly from
the browser; a developer wanting to call `:8000` straight from the browser must add CORS
themselves. (See Open questions — confirm dropping the dev-CORS path.)

### ADR-4 — Types generated from a committed `openapi.json`, drift-checked in CI
**Decision:** `scripts/dump-openapi.py` writes `web/openapi.json`; `pnpm gen:api` runs
`openapi-typescript` to produce `src/lib/api-types.ts`. Both files are committed; CI
regenerates both and fails on any diff.
**Alternatives:** generate at build time (network/DB-free but non-deterministic ordering
risk); hand-write the types; a runtime client like `openapi-fetch`.
**Why:** decision 2 with Ryan. Deterministic, reviewable diffs; `pnpm build` needs no
Python and no network (RNF-08); the wrapper stays a thin hand-rolled `fetch` (RF-03).
**Trade-off:** a two-command regen step and a CI drift job; contributors must run
`pnpm gen:api` after an API change.

### ADR-5 — TanStack Query is the only server-state store; liveness by polling
**Decision:** all API reads go through TanStack Query. "Live" views set a `refetchInterval`
function that returns an interval only while the tab is visible and some visible entity is
non-terminal, else `false`. No SSE, no WebSocket.
**Alternatives:** SSE/WebSocket from the API for scan-status push; a global store (Redux/
Zustand) mirroring server state.
**Why:** matches spec-002's polling decision (requirements §Non-goals); a single-user local
tool with short scans does not need push. Query's cache, invalidation, and `refetchInterval`
cover every need.
**Trade-off:** up to one poll interval of staleness; a burst of requests while a scan runs
(bounded: 2–3 s, one client, stops at terminal and on tab hide).

### ADR-6 — `useInfiniteQuery` for the scan list
**Decision:** the scan list is a `useInfiniteQuery` keyed by `{status}` with
`getNextPageParam: p => p.next_cursor`; "load more" calls `fetchNextPage()`.
**Alternatives:** page-number pagination with a single `useQuery` per page.
**Why:** the API exposes an opaque forward cursor only (spec-002 `Page.next_cursor`), which
maps directly onto `useInfiniteQuery`. Polling refetches all loaded pages, keeping the
visible list consistent.
**Trade-off:** polling cost grows with pages loaded; acceptable for a single user, and the
filter reset drops back to one page.

### ADR-7 — HTML report preview via sandboxed iframe + blob URL
**Decision:** the preview fetches `?format=html&download=false` with `credentials:"include"`,
wraps the bytes in a blob URL, and renders them in `<iframe sandbox="">`; the URL is
revoked on close.
**Alternatives:** a dedicated Next preview route rendering the HTML; `srcdoc`;
`dangerouslySetInnerHTML`.
**Why:** decision 4 with Ryan. Empty `sandbox` gives no script execution and no same-origin
access — the report is static HTML — and no new API route is needed.
**Trade-off:** the preview is an opaque frame (no in-app theming of the report); a blob URL
must be lifecycle-managed.

### ADR-8 — Theme by `prefers-color-scheme` only, no toggle
**Decision:** Tailwind `darkMode: "media"`; shadcn tokens defined for light and
`@media (prefers-color-scheme: dark)` in `globals.css`. No `next-themes`, no UI toggle.
**Alternatives:** `next-themes` with a class strategy and a header toggle.
**Why:** RF-02 asks only for "follows the OS preference"; a toggle needs persistence and a
hydration-safe class swap for no required benefit in 003.
**Trade-off:** users cannot override the OS theme until a later spec adds it.

### ADR-9 — E2E with Playwright driving three real processes on a temp DB
**Decision:** `playwright.config.ts` declares three `webServer` entries: (1)
`scripts/serve-fixture-app.py` (the spec-001 Starlette app, `insecure` profile) on
`:9100`; (2) `uv run webvigil-web serve` on `:8000` with `WEBVIGIL_DATABASE_PATH` pointing
at a throwaway file; (3) `pnpm start` (built Next app) on `:3000` with
`API_PROXY_TARGET=http://127.0.0.1:8000`. One chromium project. The spec scans
`http://127.0.0.1:9100`.
**Alternatives:** mock the API in the browser (defeats the point of an e2e); an
`example.com` offline fixture (decision 3 chose the Starlette app).
**Why:** decision 3 + RNF-04 — one real-browser flow against the real API and engine, fully
offline, fast (the fixture app is in-process-simple and local).
**Trade-off:** the `web` CI job needs the Python toolchain (`uv sync --all-extras`) in
addition to Node; three processes to orchestrate (Playwright handles readiness via `url`).

### ADR-10 — `next start` for tests, standalone output for Docker
**Decision:** CI e2e runs `pnpm start` (`next start` over `.next`). The Docker image uses
`output: "standalone"` and runs `node server.js` as `USER node`. `docker-compose.yml` gains
a `web` service that proxies to the `api` service.
**Alternatives:** run the standalone server in CI too; a single Node image serving both.
**Why:** `next start` is the simplest thing that applies rewrites in CI; standalone is the
smallest production image and the compose parity target (RNF-09). Both apply
`next.config` rewrites identically, so the e2e result transfers.
**Trade-off:** two run modes exercised (CI covers `next start`; the compose smoke covers
standalone).

### ADR-11 — react-hook-form + zod for the two non-trivial forms
**Decision:** the scan form and the password form use the shadcn `form` primitive
(react-hook-form + `@hookform/resolvers/zod`). Login and setup are small enough to use
plain controlled inputs.
**Alternatives:** plain `useState` everywhere; a different form library.
**Why:** the shadcn `form` component (in the fixed vendored set, decision 6) is built on
react-hook-form; zod lets the client mirror the API's rules (RF-16) in one schema, and
`fieldErrors()` reconciles server 422s onto the same fields.
**Trade-off:** two small dependencies (`react-hook-form`, `zod`) beyond the shadcn set.

## Risks

| Risk | Mitigation |
|---|---|
| Rewrite not applied the same way by `next dev` / `next start` / standalone. | E2E covers `next start`; the compose smoke covers standalone; `API_PROXY_TARGET` documented in `docs/web-ui.md`. |
| `openapi.json` / `api-types.ts` drift merged silently. | CI regenerates both and runs `git diff --exit-code` with a fix hint (RF-03, RNF-08). |
| 401 redirect loop (guard → `/login` → `/me` 401 → …). | `/login` and `/setup` are outside the guard and never call `useMe`; `keys.auth.me()` uses `retry: false`. |
| Polling burst / battery drain. | `refetchInterval` returns `false` unless the tab is visible and something is non-terminal; `refetchIntervalInBackground: false`; detail polling stops on the first terminal read. |
| `HttpOnly` cookie not sent on an `<a download>` report navigation. | Same-origin through the rewrite → cookie flows automatically; the e2e downloads the JSON report and asserts the file. |
| iframe report preview as an XSS vector. | `sandbox=""` (no scripts, no same-origin), blob URL, revoked on close (ADR-7). |
| `scripts/serve-fixture-app.py` cannot import `tests.fixtures.app`. | The Playwright `webServer` command sets `PYTHONPATH=..` (repo root) / the script inserts the repo root on `sys.path`; resolved at implementation. |
| Playwright flakiness waiting for a scan to reach `completed`. | Passive scan of the local in-process fixture app (fast, offline); a generous `expect.poll` timeout; single worker. |
| Node / pnpm version drift local vs CI. | `packageManager` pin in `package.json`; `pnpm/action-setup` reads it; `--frozen-lockfile` (RNF-11, RNF-08). |
| shadcn/Radix dependency bloat. | Fixed vendored component list (decision 6); `next build` output size reviewed; components tree-shake. |
| A page accidentally fetching during SSR/build (no DB, no API at build time). | Authed pages are client components; no `fetch` at module scope; `pnpm build` runs with no network (RNF-08) — a regression fails the build. |
| `dump-openapi.py` importing `create_app()` triggers config/DB work. | Called with `WebConfig(database_path=":memory:")`; only `app.openapi()` is invoked (no lifespan, no migrations). |

## Testing — RNF-02, RNF-03, RNF-04, RNF-05

**Component / hook (Vitest + Testing Library + MSW; no browser, no live API):**

- `api.ts`: 204 → `undefined`; `{detail}` string → `ApiError.detail` string; 422 `detail[]`
  → `fieldErrors()` map; network failure surfaces as an error.
- Auth guard: `needs_setup` → `/setup`; missing session → `/login?next=…`; valid session →
  children; `(auth)` layout redirects an authed user to `/scans`; the `next` round-trip
  after login; a mid-session 401 → `/login?reason=expired`.
- Setup form: success → `/login?setup=done`; 409 → message + link to `/login`; 422 → field
  errors.
- Login form: 401 → single generic error, password cleared, username kept; no
  username-existence disclosure.
- `ScanForm`: defaults pre-fill from `/api/config/defaults`; `active` with empty
  `authorized_by` blocks submit with the attestation message; Active-Mode warning appears;
  `disabled_checks` lists `/api/checks`; a server 422 maps back onto fields.
- Scan list: cursor pagination appends; status filter updates the URL and refetches from
  page one; polling starts with a `queued` row and stops when all rows are terminal / tab
  hidden; empty state CTA.
- Scan detail: polls while `running`, stops and refetches findings once on `completed`;
  cancel shown only for non-terminal and a 409 → toast + refetch; delete disabled for
  non-terminal, 204 → back to list.
- Findings: renders in API order (no client re-sort — RNF-01); severity + check-id filters
  sync to the URL and refetch; "no match" vs "no findings" empty states; row expansion
  shows evidence / CWE / references.
- Reports: menu disabled unless `completed`/`interrupted`; item hrefs carry
  `format`/`download=true`; preview fetches the HTML blob and mounts a sandboxed iframe.
- Settings: wrong current password (403) → inline field error; version from `/api/health`
  shown; logout clears the cache.
- **a11y (`jest-axe`):** no serious/critical violations on `/login`, `/setup`, `/scans`,
  `/scans/new`, `/scans/[id]`, `/checks`, `/settings`. Severity/status always carry an icon
  or text label, never colour alone (RNF-05).

**End-to-end (Playwright, one spec, real browser, offline — RNF-04):** three `webServer`
processes (ADR-9). Flow: open the app → redirected to `/setup` → create the account →
redirected to `/login` → log in → land on `/scans` → "New scan" → submit a **passive** scan
of `http://127.0.0.1:9100` → watch it reach `completed` → open findings → download the JSON
report and assert the saved file → `/settings` → change password → log out → back at
`/login`.

**CI:** a new `web` job (Node 20 + pnpm via `pnpm/action-setup`; `uv sync --all-extras` for
the schema dump, fixture app, and `webvigil-web`): regenerate `openapi.json` +
`api-types.ts` and `git diff --exit-code`; `pnpm lint`; `pnpm format:check`; `pnpm
typecheck`; `pnpm test`; `pnpm build`; `pnpm exec playwright install --with-deps chromium`;
`pnpm test:e2e`. The `quality` matrix and `docker` jobs are unchanged (RNF-02).

**Container parity (RNF-09):** `docker compose up --build` starts `api` + `web`; a smoke
check hits the dashboard on the published port and confirms `/api/health` resolves through
the rewrite. The `web` image runs as non-root off the standalone output.

**Gate:** `pnpm lint && pnpm format:check && pnpm typecheck && pnpm test && pnpm build`
green; `pnpm test:e2e` green; the project's Python gate (`/qualidade-python` + `uv run
lint-imports`) still green (nothing Python changed, but it is run).
